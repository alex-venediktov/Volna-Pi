# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Что это

Пакет для [pi](https://pi.dev): расширение `extensions/volna` плюс скиллы `skills/`. Ведёт одну задачу по
флоу этапов с журналом работ, адвокатом дьявола в отдельном процессе `pi`, визуальной проверкой через
CDP, викой выводов и прогоном частей подагентами. Сборки нет — pi грузит TypeScript через jiti.

## Команды

```bash
npm install                       # typescript, типы node и peer-пакеты pi
npm run check                     # tsc --noEmit, единственный линт в проекте
npm test                          # node --experimental-strip-types tests/all.ts
pi -e .                           # запустить pi с этим пакетом без установки
```

Один набор тестов вместо всех:

```bash
node --experimental-strip-types --input-type=module \
  -e "import {run} from './tests/parts.test.ts'; import {results} from './tests/harness.ts'; await run(); console.log(results());"
```

Живая проверка загрузки расширения:

```bash
printf '{"id":"1","type":"get_commands"}\n' | pi --mode rpc --no-session -e .
```

В каталоге самого пакета `.volna` нет, поэтому в списке будут только `/volna:init` и `/volna:doctor` — остальное
поднимается лишь там, где «Волна» развёрнута. Полный набор проверяется тем же вызовом из каталога с `.volna`.

Если тот же пакет ещё и **установлен** в pi (`pi install`), в развёрнутом проекте работают две копии: команды
приходят парами (`volna:task:1`, `volna:task:2`), а на одинаковых именах инструментов может выйти
`Tool "volna_init" conflicts`. Это не дефект правки — снять установленную копию или проверять тестами.

## Правила, которые видно только по нескольким файлам

**Пакет спит там, где «Волна» не развёрнута.** Инструменты, команды этапов и скиллы регистрируются только
при найденной `.volna` (`index.ts:waker` и обработчик `resources_discover`), а `registerSetupCommands` держит вне
её `/volna:init` и `/volna:doctor`. Скиллы поэтому и убраны из `pi.skills` в `package.json`: манифест грузил бы их
описания в системный промпт любого проекта. Установленный глобально пакет иначе платил бы префиксом на каждом
запросе там, где задачу никто не ведёт.

**Язык разный по адресату.** Всё, что уходит модели — описания инструментов, блок обязанностей
(`stages.ts:stageDuties`), инструкции этапов `skills/volna-flow/stages/*.md`, промпт адвоката — **по-английски
и сжато**: пакет рассчитан на локальные модели, где префикс платится на каждом запросе. Русский там, где
читают люди: журнал, сообщения команд, футер, профиль проекта, README, комментарии в коде.

**Флоу держится на инструментах, а не на просьбах в промпте.** Этап, номер итерации, метку времени и формат
секции ставит код (`core.ts`, `journal.ts`). Модель решает, что написать, а не как это оформить и когда
пометить этап пройденным.

**Зависимость от API pi только в трёх файлах**: `tools.ts`, `commands.ts`, `index.ts`. Остальное ядро —
обычный node, поэтому тесты гоняют его напрямую без моков pi. Новый код по возможности класть в ядро.

**Имя этапа одно в четырёх местах**: `STAGES` в `stages.ts`, файл `skills/volna-flow/stages/<имя>.md`,
значение `stage` во frontmatter журнала, хвост имени команды `/volna:<имя>`. Расхождение значит, что что-то
одно неверно.

**Команда и инструмент идут одной дорогой.** `/volna:analyze` и `volna_stage` вызывают одну функцию ядра —
расхождение «человек нажал» против «модель решила» было бы источником самых непонятных ошибок.

## Раскладка

| Модуль | О чём |
|---|---|
| `core.ts` | приём задания, вход в этап, пропуск, закрытие части и задачи, шапка, сводка |
| `journal.ts` | два файла журнала: frontmatter + «Состояние» и append-only лог итераций |
| `parts.ts` | задача из нескольких частей: список в «Состоянии», `part`/`parts` во frontmatter |
| `assignment.ts` | задание текстом или ссылкой на файл (путь, `@`, `file://`, `~`) |

| `changes.ts`, `diff.ts` | правки для адвоката из git diff против точки начала части, свой unified diff |
| `git.ts` | доставка: ветка задачи, коммит части, push (единственное, что «Волна» пишет в VCS) |

| `piagent.ts` | общее для обоих подпроцессов: как позвать pi и как прочитать его поток событий |
| `wiki.ts` | вика выводов: соглашения, разбор записей, якоря, сверка цитаты с источником |

| `wiki-lint.ts` | структурные проверки записей и файлов, коды K001-K024 |
| `wiki-ops.ts` | операции целиком: развернуть, собрать, проверить, сверить, посчитать |
| `visual.ts`, `cdp.ts` | браузер pi-chrome-devtools по Chrome DevTools Protocol |
| `index.ts` | события pi: шапка, гейт правок, отмена сжатия, футер |

## Инварианты журнала

`.volna/journal/TASK-<id>.md` — frontmatter и переписываемая секция «Состояние», по ней задача
восстанавливается с нуля. `logs/TASK-<id>.log.md` — append-only, прошлые секции не переписываются никогда.
При противоречии слоёв прав файл состояния.

- **Имена подпунктов «Состояния» фиксированы** (`STATE_LABELS`): подпункт с другим именем никто не найдёт —
  ни `journalIssues`, ни шапка, ни следующая сессия.
- **`state_sync`** хранит последнюю секцию лога на момент перезаписи «Состояния». Отставание по меткам
  времени не поймать: формат меток до минут, запись и перезапись попадают в одну минуту.
- **Список частей переносится сам**, когда `action=state` вызвали без него: он источник правды об остатке, и
  забытое поле стёрло бы остаток задачи.
- Метки времени берутся у часов машины: по ним на закрытии считаются часы.

## Границы версии

Доставка есть только в git и только по профилю (`доставка`, `ветка`, `база`, `удалённый`): `нет` означает,
что этапа `deliver` в проекте не существует. Этап стоит перед `close`, то есть внутри цикла части: одна
ветка на задачу, коммит (и не один, если часть того требует) на каждую часть. Push спрашивает согласие
человека и не делается без него; force push не делается никогда. **Правки «Волна» читает только из git**:
своего трекинга изменений у неё нет, других систем контроля версий она не знает, и без git этап `advocate`
отказывается работать, а не проверяет проект целиком. Остальной флоу вне git идёт как обычно. Трекера и PR
нет: профиль эти строки описывает, этапы про них знают, кода под них нет.

**Граница поиска `.volna`** (`paths.ts:findVolnaDir`): подъём вверх останавливают каталог с `.git`
(чужой репозиторий), корень диска и домашний каталог. Вне git первых двух признаков мало: без границы
`~/.volna`, развёрнутая когда-то не там, становится настройкой для всего, что под ней. Параметр
`stopAbove` существует ради теста — в бою он всегда `homedir()`.

**`.gitignore` заводится только в git-репозитории.** Вне git `init` разворачивается, но говорит, чего в
проекте не будет (`InitResult.warnings`), и правил не пишет.

**База адвоката — точка начала части, а не `HEAD`.** SHA пишется во frontmatter (`part_base`) на первой
итерации `implement` и сбрасывается закрытием части. Иначе коммит внутри части (в том числе на `deliver`)
уводил бы проверенное из-под адвоката, а при `доставка: нет` дифф следующей части приходил бы вместе с
предыдущей.

## Инварианты вики

`.volna/wiki/` коммитится, в отличие от журнала: журнал - ход работы одного человека, вика - знание команды.
Запись заводит этап `capture`, и стоит он перед `deliver` ровно затем, чтобы запись уехала тем же коммитом,
что и работа.

- **Единица хранения - вывод, а не страница про сущность.** Заголовок это утверждение; поля `тип`,
  `предмет`, `этапы`, `вывод` обязательны, а имена полей русские: формат записи - данные, а не промпт.
- **Указатели собираются, а не пишутся** (`wiki-ops.ts`, действие `index`): ручная правка затирается, а
  мёртвые шарды сборка удаляет - указатель переименованного узла выглядит живым и отдаёт устаревший перечень.
- **Набор этапов вики берётся у флоу** (`wiki.ts`, `DEFAULTS.stages` = `STAGE_NAMES`): свой список
  разошёлся бы с `STAGES` и забраковал записи с законными этапами (`K008`).
- **Относительный корень сверки отсчитывается от корня проекта**, а не от каталога процесса
  (`wiki-ops.ts:projectRootOf`): pi запускают и из подкаталога, и тогда `root: "."` превратил бы живые
  якоря в «файла нет», а линт остался бы чистым.
- **Без `fix` ни одна операция в файлы не пишет.** Коды возврата те же, что у CLI плагина: 0 чисто,
  1 ошибки, 2 только предупреждения, 3 сбой.
- Из плагина не перенесены `flatten` и `migrate` (миграции истории, которой у pi-пакета не было) и
  разведочный `wiki-survey`.

## Подагенты

Подагент законен как чтение внутри этапа - сходить, прочитать много, вернуть короткий вывод. Ветвью флоу он
не становится, и упирается это не в цену, а в устройство: журнал один, `state.json` указывает на одну
активную задачу и по ней держит гейт правок, параллельные ветви дают гонку записи.

`/volna:parts-run` и `volna_part` гонят незакрытые части по одной. Подагент здесь **работник, а не вторая
ветка флоу**: расширения «Волны» ему выключены (`runner.ts`), поэтому инструментов этапа, журнала и гейта у
него нет вовсе - он делает работу одной части и отчитывается пятью полями, а этапы, адвокат, тесты и
закрытие части остаются на оркестраторе. Условия запуска проверяет код (`partsRunReadiness`): активная
задача, больше одной незакрытой части, не отставший журнал. Всё, кроме `ИТОГ: сделано`, прогон останавливает:
независимость частей - оценка, сделанная до работы.

Права на запись у подагента настоящие, и запрет коммитить держится промптом, а не устройством: `bash` ему
нужен для проверок проекта.

## Тесты

`tests/harness.ts`: `check(label, condition, extra)`, `sandbox(name, {git})`, `exec` с контрактом `pi.exec`,
`toolText`. Новый набор — файл `tests/<тема>.test.ts` с `export async function run()` плюс строка в
`tests/all.ts`. Метки проверок по-русски, утверждением о поведении.

Модели тесты не касаются: проверяется то, что должно работать одинаково при любой модели. Инструменты
тестируются через `registerTools` с поддельным `pi`, события — через вызов `volna(fakePi)`.

## Профиль проекта

`.volna/project.md`, секция `## Профиль`. Правило: **чего в профиле нет, того этап не делает** — молча, без
записи «пропущено». Значение в угловых скобках (`<chrome-devtools|нет>`) значит «не спрошено»: этап
останавливается и спрашивает, а не догадывается (`state.ts:isPlaceholder`).
